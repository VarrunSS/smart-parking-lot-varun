    policy = new class + one registratio
  - StandardHourlyPolicy: composes HourlyRateSchedule (3/$2 tiers) and IPeakPeriodRule (WeekdayPeakRule:
    windows 07-10 / 16-19, start inclusidayCalendar). Builds floating one-hour blocks
    and applies 1.5x on any overlap.

    LoyaltyDiscount application. EarlyBirdPolicy and NightOwlPolicy extend it and supply only their windows and

  - PricingEngine(IEnumerable<IPricingPolicy>): evaluates all, returns the minimum as FareQuote(PolicyName,
    Money). Throws if none applies (cannegistered).
  - PricingEngineFactory.CreateDefault(IHolidayCalendar): the single composition point listing the policies, so
    removing or adding one is a one-line
- Facility/: ParkingLot facade: IssueTicket(vehicleType, spotType, entryTime, tier) (rejects incompatible spot)

You're right on both. The nested folders were my invention, and IHolidayCalendar shouldn't be in Pricing.
IHolidayCalendar: I put it under Pricing/Hourly because WeekdayPeakRule is its only consumer. But it describes
external data (what counts as a holiday), not pricing logic. The factory takes it too, so a pricing folder is thewrong owner. Calendar/ is a better home. I'd put TimeWindow there as well, since it's a time-of-day window and fits
the same idea.
Flat top-level folders: I agree. There are only about 25 files, and a third level of nesting is more structure thanthat needs. Here is the layout I'd use:
Domain/    Money, Ticket, ParkingSession, VehicleType, SpotType, LoyaltyTier, exceptions
Calendar/  IHolidayCalendar, EmptyHolidayCalendar, TimeWindowRules/     IPeakPeriodRule, WeekdayPeakRule
Pricing/   IPricingPolicy, StandardHourlyPolicy, HourlyRateSchedule,           DiscountedFlatRatePolicy, EarlyBirdPolicy, NightOwlPolicy
Billing/   PricingEngine (+FareQuote), PricingEngineFactory, FareCalculator
Dependencies run one way: Billing -> Pricing -> Rules -> Calendar -> Domain. Domain and Calendar depend on nothingelse.

- Less churn: SmartParking.Domain and SmartParking.Pricing keep their namespaces. Facility becomes Billing, and  Calendar, Rules and Billing are new. Fewer using edits in src and tests.

  and new rules would go there.- DDD: this is a pragmatic layout by concept. It drops the strict Parking-versus-Pricing subdomain split I proposed.
